### Находки разведки торгового пути — 10.09.2026

Разбор клиента биржи, исполнителя и журнала сделок перед Фазой 3.B–3.D. Каждая
находка — к задаче плана; все, кроме помеченных «бумага», блокируют TESTNET/LIVE.

### Находки к задаче 3.4 — бумажная торговля с балансом 100 $

Найдено при разборе кода 10.09; каждая влияет на то, будут ли бумажные результаты похожи на реальные.

1. **Начальный баланс задан дважды.** `INITIAL_BALANCE = 10000.0` и в `config.py`, и отдельной константой в `capital.py`; разные модули читают разные копии.
2. **Две модели размера позиции, и Risk Core проверяет не ту.** `signal_generator` считает размер от риска на сделку (`capital.position_size`: 2 % доступного / расстояние до стопа). Risk Core оценивает это число (гейткипер, строка ~221). Через двести строк `PositionSizer` затирает его своим: `баланс × final_risk % / 100` — доля баланса как номинал. В сделку уходит второе число, прошедшее проверку риска только косвенно.
3. **При 100 $ вторая модель даёт позицию около 1 $.** `final_risk` зажат в 0,1–3 %, то есть номинал 0,1–3 $. Минимальный ордер на Bybit — от 5 $ по номиналу, у BTC около 78 $ (0,001 BTC). Реальная биржа такие ордера отклонила бы, а бумажная торговля их «исполнит».
4. **Бумажный PnL без комиссий.** `trade_manager._calc_pnl` — только изменение цены × номинал. Поле `commission` в схеме есть, но всегда 0. Taker на Bybit — около 0,055 % с каждой стороны.
5. **Слитый счёт маскируется.** База не опускает баланс ниже 10 $ (`get_current_balance_from_db`, `max(..., 10.0)`), а `risk_exposure_brain` при балансе ≤ 0 подставляет начальный. При счёте в 100 $ «пол» в 10 $ — это 10 % капитала, которых нет. Фронтенд — 12 тестов, харнесса раньше не было. Покрытие ядра решений 84 % (гейт 80 %), всего проекта 23 % — путь до денег (`api/` 0 %, `execution/` 7–22 %) почти не покрыт, это задача 3.18.

### Что выяснила разведка прод-сервера (влияет на Фазы 3–4)

Прод — хост в РФ, где уже работает соседний проект со стеком Supabase. 4 CPU, 5,8 ГБ RAM,
из них ~2,6 ГБ занимает стек Supabase; свободно ~3,2 ГБ. Домен вида
`<ip>.sslip.io` с сертификатом Let's Encrypt, обновляется `certbot.timer`.

Три факта, которых не было в аудите и которые меняют план:

1. **`api.telegram.org` с этого адреса недоступен** — соединение отваливается по
   таймауту (HTTP 000). Бот без прокси не заработает вообще. На хосте уже поднят
   `sing-box` (`mixed` inbound на портах 12334 и 12335), через него Telegram
   отвечает 302. В `ufw` порт 12334 уже открыт для `172.16.0.0/12`, то есть для

2. **Bybit с этого же адреса доступен напрямую** — 0,28 с против 0,36 с через
   прокси. Гео-блока нет, торговый трафик прокси не требует и не должен через
   него идти.
3. **Полный стек мониторинга из Фазы 4 в 3,2 ГБ не влезает** рядом с Supabase.
   Prometheus + Grafana + Alertmanager + три экспортёра — это ~1 ГБ и четыре
   лишних порта. Задача 4.3 переопределяется: алерты уходят в Telegram напрямую
   из бота (у него уже есть канал доставки), `/metrics` остаётся для будущего
   Prometheus, а Grafana откладывается до отдельного решения владельца.
   Экономия ~1 ГБ и минус три публичных сервиса на периметре.

Наработки, которые стоит перенести из соседнего проекта на том же хосте (его deploy.sh, 17 КБ):
деплой-скрипт живёт на сервере и в git одновременно (в allowlist разрешён запуск
только его, а не произвольный ssh); артефакты стейджатся в `/tmp/deploy` через scp
до запуска; успешный шаг убирает свой staging, упавший — оставляет для повтора;

жадного кэша Telegram WebView и `immutable` на хэшированные assets.

## 0. Принципы работы по плану

1. **Порядок фаз обязателен.** Фаза 1 (CI) раньше любых правок кода, иначе каждая правка идёт вслепую. Фаза 3 (торговля) не начинается, пока не закрыта Фаза 2 (доступ).

3. **Definition of Done для каждой задачи:** код + тест, который падал бы без правки + запись в CHANGELOG + критерий приёмки из этого плана выполнен командой, а не словами.
4. **Прод до Фазы 4 не трогать**, кроме шага 0.4 (проверка, что отозванный токен заменён и бот жив). Cron-деплой на время работ отключить: `crontab -e`, закомментировать строку `deploy.sh`.
5. **Режим торговли до конца Фазы 3 — только `DRY_RUN`.** Проверяется гейтом в CI (задача 3.1).
6. Каждая фаза заканчивается **контрольной точкой** с командами проверки. Не переходить дальше, пока все команды контрольной точки не зелёные.
