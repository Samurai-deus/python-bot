## 1. Гигиена — ✅ 11.09

### 1.1 Пакет `signals/` затеняет модуль `signals.py`

**Факты.** В корне лежат и модуль `signals.py`, и пакет `signals/` (только `__init__.py`, коммит 021e909). Python выбирает пакет; его `__init__.py` через `importlib.util.spec_from_file_location` загружает `signals.py` как отдельный модуль `signals_module` и переносит из него `build_signal`. Проверено: `import signals` → `signals/__init__.py`, `build_signal` есть. Импортируют `signals` двое: `execution/gatekeeper.py:31` и `tests/test_market_state_contract.py`.

**Чем плохо.** Один и тот же код живёт в памяти под двумя именами: подмена в тесте (`monkeypatch` на `signals_module` или на `signals`) действует только на одну копию; ошибка загрузки внутри `try` в `__init__` превращается в непонятный `ImportError` в гейткипере.

**Шаги.**
1. Удалить каталог `signals/`: `signals.py` станет единственным кандидатом.
2. Тест: `signals.__file__` оканчивается на `signals.py`, `build_signal` импортируется.
3. Полный набор тестов, импорт `runner` без окружения (шаг CI «Импорт без окружения» уже есть).

**Доказательство.** Тест из шага 2; на проде — первое сообщение о сигнале приходит (гейткипер строит его через `build_signal`). **Откат** — revert PR.

### 1.3 Флейк `tests/test_liveness.py` на Windows

**Факты.** `utils/liveness.mark()` пишет метку во временный файл и делает `os.replace`. На Windows антивирус на мгновение держит только что записанный файл, и `os.replace` получает `WinError 5`; метка не ставится, тест `test_stalled_event_loop_is_unhealthy` падает. 11.09 — 1 падение из 3 на чистом main. На Linux (прод, CI) такого нет.

**Шаги.** Повтор `os.replace` при `PermissionError` — до 3 раз с паузой 50 мс; тест с подменой `os.replace`, который дважды бросает `PermissionError`, — метка ставится. Бот на Linux поведение не меняет.

## 4. 2.8 — серверная сессия вместо initData на сутки — 🔄 выкладка 2 из 3

**Факты.**
- API принимает initData из заголовка `X-Telegram-Init-Data` 24 часа (`api/deps.py`, `INIT_DATA_MAX_AGE = 86400`) без защиты от повтора; WebSocket — то же initData в первом сообщении.
- Подпись проверяется верно (HMAC, `compare_digest`, `auth_date` внутри подписи), допуск — `utils/principals`, initData в логи и Sentry не попадает (задачи 2.1, 2.10).
- **Тот же initData даёт права владельца**: `verify_admin` — это `verify_auth` плюс проверка `user_id`. Утёкший initData (снимок экрана devtools, промежуточный прокси, чужой лог) — это 24 часа не только чтения финансов, но и записи: `PUT /api/settings/keys` (ключи биржи), `PUT /api/settings`.
- Окно нельзя просто сократить: initData выдаётся при открытии Mini App и без переоткрытия не обновляется — открытое приложение упало бы в 401.
- Redis уже доступен API (лимит запросов, `api/rate_limit.py`); он без персистентности (`--save ''`) — после его перезапуска сессии теряются, владелец переоткрывает Mini App.

**Реальный риск — средний.** Для утечки нужен доступ к устройству или каналу владельца, но последствия — права владельца на сутки.

**Устройство.**
- `POST /api/auth/session`: принимает initData **не старше 1 часа** и **однократно** (hash initData — `SET NX` в Redis с TTL 1 ч; повтор → 401). Выдаёт непрозрачный токен (`secrets.token_urlsafe(32)`); в Redis хранится `sha256(токена)` → `{user_id, is_admin, created_at}`.
- Сессия: скользящее окно 12 ч без активности, абсолютный предел 24 ч (как сейчас у initData). Непрозрачный токен в Redis, а не JWT из исходного плана: отзывается удалением ключа (например, при ротации токена бота), не нужен ещё один секрет подписи.
- Все роуты и WebSocket принимают `Authorization: Bearer <токен>`.
- **Опасные записи** (`PUT /api/settings/keys`) дополнительно требуют initData не старше 10 минут в том же запросе — даже украденная сессия не меняет ключи биржи.
- Redis недоступен: выдача сессий — 503; чтение — по initData с окном 1 ч (деградация с логом-предупреждением); запись — отказ.
- Фронт: при старте обменивает initData на токен, держит его **в памяти** (не в localStorage); на 401 — одна попытка обмена заново, если initData младше часа, иначе прежний баннер «откройте снова из Telegram». WebSocket авторизуется токеном.

**Выкладки.**
1. **API принимает оба способа** (initData на сутки — как сейчас — и сессию). Ничего не ломается для открытого приложения и закэшированного фронта.
2. **Фронт переходит на сессию.** Владелец открывает Mini App: данные грузятся, WebSocket живой.
3. **Через 2 дня** — initData принимается только в `/api/auth/session` (1 ч, однократно) и в заголовке опасных записей (10 мин).

**Тесты.** pytest: обмен работает; повтор того же initData → 401; initData старше часа → 401; сессия работает, когда initData уже старше часа (подмена времени); скользящее и абсолютное истечение; запись ключей без свежего initData → 403; Redis недоступен — чтение по initData ≤ 1 ч, запись отказ; WebSocket с токеном. vitest: перехватчик делает один повторный обмен и затем показывает баннер. Smoke на проде расширяется: обмен подписанного в контейнере initData → 200 с сессией; повтор → 401.

**Откат.** Выкладка 3 отменяется возвратом одной константы; 2 — `web-rollback`; 1 — revert.

После каждой выкладки — smoke и один полный оборот цикла анализа в логах.
3. **Пакеты `bot/`, `trading/`, `infra/`** — не сейчас; имеет смысл, только если над кодом начнут работать несколько человек.

**Доказательство.** После каждого PR: полный набор тестов, тест импортов, `import runner` без окружения, smoke; `runner.py` уменьшается, поведение — нет.
